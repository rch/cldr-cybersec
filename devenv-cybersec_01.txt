  Cybersec Toolkit Analysis

  Current State

  The toolkit is highly Kafka-centric - almost every component reads from or
   writes to Kafka topics. However, the architecture uses abstract base 
  classes with Kafka-specific implementations, which provides a path
  forward.

  Components That Could Work Standalone (No Kafka/HBase)

  | Component                          | Standalone? | Notes
                            |
  |------------------------------------|-------------|----------------------
  --------------------------|
  | Parser Chains (parser-chains-core) | ✓           | Pure parsing logic,
  decoupled from I/O         |
  | CIDR Enrichment                    | ✓           | Uses ipaddress
  library, config file only       |
  | GeoIP/ASN Enrichment               | ✓           | Uses MaxMind database
   files                    |
  | Flink Table API Jobs               | ✓           |
  CloudTrailDataGenIcebergJob already works!     |
  | Caracal Generator                  | ~           | Uses Freemarker
  templates, but writes to Kafka |

  The Hadoop Tar Pit Problem

  The existing toolkit heavily depends on Hadoop classes via:
  1. Flink core fs (Path, FileSystem) - Used for reading configs
  2. HBase dependencies - Default enrichment backend
  3. Avro/Parquet - Through Hadoop's implementations

  However, our devenv already has a working Hadoop-free path via:
  - Iceberg REST Catalog (Apache Polaris) - No Hive metastore
  - MinIO with S3 protocol - No HDFS
  - PostgreSQL for catalog metadata - Not HBase

  Recommended Strategy

  Phase 1: Use Existing Java Iceberg Job
  The CloudTrailDataGenIcebergJob at flink-cyber/flink-common/src/main/java/
  .../CloudTrailDataGenIcebergJob.java:43 already:
  - Uses Flink's built-in datagen connector (no Kafka)
  - Writes directly to Iceberg via REST catalog
  - No Kafka, HBase, or HDFS dependencies

  We could run this Java job right now instead of the Python datagen.

  Phase 2: Create Minimal Standalone Modules

  Create new "lite" implementations that bypass Kafka:

  flink-cyber-lite/
  ├── parser-chains-lite/     # ParserJob → FileSource/IcebergSink
  ├── enrichment-lite/        # CIDR + GeoIP only (no HBase lookups)
  └── datagen-lite/           # DataGen → Iceberg (already exists!)

  The key pattern from ParserJob:
  // Abstract methods - implement these differently
  protected abstract DataStream<MessageToParse> createSource(...);
  protected abstract void writeResults(...);

  Phase 3: Wire Into DevEnv

  Replace our Python datagen with the Java one, or create a minimal
  pipeline:
  DataGen → Parser (optional) → CIDR/Geo Enrichment → Iceberg

  What to Avoid

  1. HBase dependencies - All flink-enrichment-lookup-hbase code
  2. Kafka connectors - Use DataGenTableSource or file sources instead
  3. Avro schema registry - Use JSON or Iceberg's schema evolution
  4. Cloudera SMM (monitoring-interceptors) - Kafka-specific

  Quick Win: Run the Java DataGen

  We could immediately test the Java Iceberg job:

  cd flink-cyber && mvn clean install -pl flink-common -am -DskipTests
  flink run -c com.cloudera.cyber.flink.iceberg.CloudTrailDataGenIcebergJob
  \
    flink-common/target/flink-common-*.jar \
    --catalog.uri http://localhost:8181 \
    --warehouse s3://cybersec/iceberg/warehouse \
    --rows-per-second 10

  This would validate that the Java toolkit can integrate with our devenv
  infrastructure.
